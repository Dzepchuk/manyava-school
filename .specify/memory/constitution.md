# Конституція офіційного вебсайту Манявського ліцею Солотвинської селищної ради

## Основні принципи

### I. Законність і прозорість

Сайт MUST забезпечувати оприлюднення інформації, обов'язкової для закладу освіти
відповідно до чинного законодавства України. Кожна юридично значуща вимога MUST
мати посилання на нормативне джерело, дату перевірки та відповідального за
підтвердження. Неперевірені правові припущення MUST бути явно позначені та не
можуть подаватися як остаточна юридична вимога.

Обов'язкова інформація MUST бути доступною без авторизації, мати стабільну адресу
та визначеного власника контенту. Офіційні документи MUST публікуватися у формі,
що зберігає їхню цілісність, дату, назву та контекст.

### II. Приватність і безпека дітей за замовчуванням

Система MUST мінімізувати збирання, зберігання й оприлюднення персональних даних.
Персональні дані учнів, списки учнів, дитячі контактні дані, оцінки та інші
чутливі відомості MUST NOT бути загальнодоступними без документованої правової
підстави. Фото й відео з дітьми MUST оброблятися відповідно до затвердженої
школою політики та підтвердженої підстави для публікації.

Форми MUST збирати лише дані, необхідні для заявленої мети, пояснювати мету
збирання та строк зберігання, а також захищати дані від випадкового розголошення.
Нові функції MUST проходити окрему оцінку впливу на приватність і безпеку дітей.

### III. Доступність та інклюзивність

Усі публічні функції MUST бути доступними з клавіатури, мати семантичну структуру,
зрозумілі назви елементів, достатній контраст і коректну роботу зі скринрідерами.
Зображення, що передають зміст, MUST мати змістовний альтернативний опис. Зміст
MUST NOT передаватися лише кольором, положенням або звуком.

Інтерфейс MUST залишатися придатним до використання при масштабуванні щонайменше
до 200 відсотків. Кожна користувацька історія MUST містити перевірювані критерії
доступності. Виявлений критичний бар'єр доступності блокує випуск функції.

### IV. Мобільність і продуктивність

Основні сценарії MUST проєктуватися спочатку для мобільного телефона та повільного
або нестабільного з'єднання. Ключова інформація MUST бути доступною без
горизонтального прокручування та не більше ніж за три змістовні переходи від
головної сторінки.

Специфікація кожної публічної функції MUST визначати вимірювані користувацькі
показники швидкодії. Зображення, документи та сторонні інтеграції MUST NOT
створювати невиправданих затримок або блокувати доступ до основного змісту.

### V. Якісний контент і просте адміністрування

Працівник школи без технічної підготовки MUST мати змогу виконувати регулярні
операції з контентом без зміни коду: публікувати новини й оголошення, додавати
документи та події, змінювати контакти й приховувати застарілий матеріал.

Кожен тип контенту MUST мати власника, статус публікації, дату створення, дату
останнього перегляду та правила архівування. Основний зміст MUST публікуватися як
доступний HTML; PDF використовується для підписаних або форматно значущих
офіційних документів, але не як єдиний спосіб подання критичної інформації.

### VI. Специфікація, трасованість і перевірка

Специфікація є джерелом правди для поведінки системи. Кожна функціональна вимога
MUST мати унікальний ідентифікатор, критерії приймання та зв'язок із
користувацькою історією. Реалізаційні задачі й автоматизовані перевірки MUST
посилатися на відповідні вимоги.

Ланцюжок `вимога → критерій приймання → задача → код → тест` MUST бути
відновлюваним під час перевірки. Зміна поведінки, структури даних, ролей,
архітектури, безпеки або приватності MUST супроводжуватися зміною відповідної
специфікації. Функція не завершена, доки її критерії приймання не перевірені.

### VII. Простота та відтворюваність

Рішення MUST бути найпростішим, що повністю задовольняє перевірені вимоги.
Невикористані абстракції, передчасна універсальність і функції поза погодженою
областю MUST NOT додаватися. Винятки потребують письмового обґрунтування у плані.

Проєкт MUST збиратися, тестуватися та розгортатися відтворювано з Git-репозиторію.
Контент і конфігурація, необхідні для відновлення сайту, MUST мати документоване
резервне копіювання. Критичні зовнішні залежності MUST мати описану поведінку при
недоступності.

## Обов'язкові обмеження та критерії якості

- Робоча мова специфікацій і користувацького інтерфейсу — українська.
- Англійська допускається для коду, ідентифікаторів, назв технологій, протоколів
  і термінів, переклад яких знижує точність.
- Публічні сторінки MUST працювати без облікового запису, крім функцій, для яких
  авторизація прямо обґрунтована вимогами.
- MVP MUST NOT містити власний електронний журнал, оцінки, учнівські кабінети,
  внутрішню соціальну мережу, чати, онлайн-оплату або повноцінний електронний
  документообіг.
- Аналітика MUST мінімізувати відстеження, не використовувати приховане
  профілювання та не збирати персональні дані без підтвердженої потреби.
- Безпека, доступність, приватність, резервне копіювання та відновлення MUST бути
  критеріями приймання, а не відкладеними покращеннями.

## Процес розробки та контрольні точки

1. Кожна суттєва функція проходить етапи: `constitution → specify → clarify →
   plan → tasks → analyze → implement → acceptance`.
2. Специфікація визначає WHAT і WHY без передчасного вибору технологій.
3. План визначає HOW і MUST пройти Constitution Check до дослідження та після
   проєктування.
4. Задачі MUST бути згруповані за незалежно перевірюваними користувацькими
   історіями та містити точні шляхи до файлів.
5. Автоматизовані тести MUST створюватися для критичних сценаріїв, контролю
   доступу, публікації контенту, доступності та захисту даних.
6. Перед завершенням зміни MUST бути виконані релевантні тести, перевірка
   критеріїв приймання й аналіз узгодженості артефактів.
7. Перший вертикальний зріз: головна сторінка → список новин → сторінка новини →
   створення та публікація новини редактором → перевірка доступності →
   відтворюване розгортання.

## Governance

Ця конституція має пріоритет над іншими проєктними документами у випадку
суперечності. Зміна принципів потребує письмового обґрунтування, опису впливу на
наявні специфікації та плану міграції, якщо змінюється вже реалізована поведінка.

Версія конституції змінюється за Semantic Versioning:

- MAJOR — несумісне вилучення або переосмислення принципу;
- MINOR — новий принцип або суттєве розширення обов'язкових правил;
- PATCH — уточнення без зміни змісту правил.

Кожен план і pull request MUST містити перевірку відповідності конституції.
Відхилення MUST бути явно задокументоване у Complexity Tracking із причиною та
аналізом простішої альтернативи. Конституція переглядається щонайменше перед
кожним великим етапом дорожньої карти та після зміни законодавчих або
організаційних вимог.
