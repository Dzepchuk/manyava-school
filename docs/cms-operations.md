# Робота з редактором сайту

## Ролі на старті

### Технічний адміністратор

- має окремий GitHub-акаунт із роллю repository `Admin` та MFA;
- налаштовує GitHub OAuth у Netlify, branch protection, required checks і
  deployment;
- додає та відкликає користувачів, керує секретами й схемами;
- публікує контент лише як аварійна заміна директора із записом причини.

### Директор

- має окремий GitHub-акаунт із роллю repository `Write` та MFA;
- працює через `/admin/`, створює, перевіряє й публікує контент;
- не отримує доступу до OAuth secrets, billing або керування користувачами.

Спільні акаунти заборонені. Новому користувачу надається найменша достатня роль.

## Початкове налаштування

1. Підключити repository `Dzepchuk/manyava-school` до Netlify.
2. У Netlify додати GitHub як authentication provider. OAuth client secret
   зберігати тільки в налаштуваннях Netlify.
3. Захистити `main`: заборонити прямий push, вимагати pull request і успішні
   content/build/test checks.
4. Надати директору GitHub `Write` після перевірки MFA.
5. Відкрити `/admin/`, виконати вхід і створити непублічну навчальну чернетку.

Локальний `/admin/` використовує той самий віддалений GitHub backend. Не
зберігайте тестові production credentials у браузері на спільному пристрої.

## Публікація

1. Створити запис і заповнити заголовок, опис, дати та відповідального.
2. Для зображення вказати alt, розмір, ліцензію/дозвіл, затвердження та правову
   підставу, якщо на ньому є діти.
3. Зберегти як чернетку. Decap створює гілку й pull request, а production не
   змінюється.
4. Відкрити Netlify preview і перевірити текст, мобільний вигляд, посилання та
   зображення.
5. Публікувати лише після успішних перевірок. Merge в `main` запускає production
   deployment.

Небезпечний HTML, iframe/script, недозволені URL, файли або неповні права на
медіа блокують збірку. Повідомлення перевірки містить файл, поле, код правила та
безпечну підказку українською.

## Архівування

Матеріал не видаляють. У полі `status` виберіть `archived`, перевірте preview і
опублікуйте зміну. Він зникає з актуальних списків, але залишається в Git.

## Конфлікт редагування

1. Не публікувати pull request із Git conflict.
2. Визначити, яка версія містить останній підтверджений зміст.
3. Технічний адміністратор вирішує conflict у feature branch.
4. Директор повторно перевіряє preview перед merge.

Silent last-write-wins не допускається.

## Відновлення попередньої версії

1. Знайти merge commit, який додав неправильний контент.
2. Створити окрему recovery branch.
3. Виконати `git revert <commit>`, push і pull request.
4. Перевірити Netlify preview та required checks.
5. Merge revert у `main` і перевірити production.

Не використовуйте force push або переписування історії `main`.

## Додавання та відкликання доступу

### Onboarding

1. Письмово підтвердити особу й потрібну роль.
2. Переконатися, що акаунт персональний і MFA увімкнено.
3. Надати мінімальну GitHub-роль.
4. Провести тест із чернеткою без персональних даних.
5. Записати власника доступу та дату наступної перевірки.

### Revocation

1. Негайно видалити користувача з repository/team.
2. Відкликати пов’язані Netlify sessions або provider access.
3. Закрити чи передати відкриті content pull requests.
4. Перевірити, що повторний вхід, push і publish недоступні.
5. Записати дату, виконавця та результат перевірки.

Доступи переглядаються після кадрових змін і щонайменше раз на пів року.
